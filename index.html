From idea to a release someone can use

1. Define the first useful outcome

Write the user, their problem, one core journey and a measurable success criterion. Sketch the screen or interface and include one failure case. List what you’ll defer. Ask ChatGPT or Claude to challenge assumptions, then show a rough prototype to a representative user before investing in more features.

2. Set up a repeatable local build

Use the simplest supported stack you know that fits the requirements. Record the runtime version, setup and test commands in the README. Check in a lockfile when your tooling supports one. Use synthetic data and placeholder environment variables. Run the starting app and relevant checks, then record the baseline and create a branch.

In an existing Git repo, run git status to inspect local work and git rev-parse --short HEAD to record the baseline. When you’re ready, create a task branch with git switch -c feature/first-slice.

3. Implement one end-to-end slice

Give the assistant the accepted behavior, current commit, relevant files and allowed changes. Use Codex for a focused patch when available. In a chat-only session, ask for a small diff or a few specific edits, inspect them, and apply them in your editor. Commit the slice after you can explain the change and demonstrate the behavior.

Review changes with git diff and review staged changes with git diff --staged. Check the exact edits and the test output before you commit.

4. Verify real behavior and debug one failure at a time

Run the project’s checks and exercise its normal entry point. Test success, invalid input and recovery. For multi-user products, confirm users can see and change only their own permitted data. For a bug, capture the expected and observed behavior, smallest reproduction and exact error. Check one hypothesis at a time and add a regression test where it can catch a repeat.

5. Review, release and recover

Give Claude Free or a teammate the original brief, sanitized diff and actual test results. If you have one assistant, start a fresh review chat with the same evidence and verify its findings yourself. Decide what to fix, rerun affected checks, then release to a small audience. Record the release commit, smoke test, previous working release and recovery steps. For releases that change persistent data, test backup and restore first.

6. Learn from usage and keep operating costs visible

Ask whether users can complete the first journey and where they get stuck. Fix the biggest obstacle before adding features. Track errors and the owner of each service. Hosting, databases, email, domains, app distribution and runtime AI can each have separate limits or costs. Check plan terms and quotas before connecting a paid dependency. For an AI feature, start with sample responses and test empty, error and timeout states before wiring a provider.

When your free allowance runs out

Save a short checkpoint in your repo or task tracker with the goal, acceptance criteria, base commit, branch, changed files, commands and results, and the next smallest step. Keep testing and reading official docs locally. Resume with that checkpoint in a fresh chat or another approved tool when available. Resolve conflicting suggestions against the requirements, source code and tests.

Keep API keys, customer data, credentials and restricted code out of public AI chats. Share approved excerpts or a minimal example with synthetic data. If the material cannot be shared, continue locally or use an approved environment.

Pick the first slice for your product

Web or SaaS
Start with one page and one useful action. For a task tracker, add a task, reject a blank title and verify the task survives a reload. Add sign-in and shared storage when the user journey calls for them.
Mobile or desktop
Start with one screen, local data and a restart check. Prove the core action on a supported target device before tackling distribution, syncing or permissions.
API, CLI or automation
Run one command or endpoint against a representative fixture. Verify the expected output, a rejected input and recovery after a failure. For a job that writes data, check what happens when it runs twice.
AI-powered product
Choose one measurable task such as extracting fields from a sample document. Start with fixtures and a predictable mock. Evaluate against expected outputs and decide how production data, availability and usage costs will be handled.

YOUR PRACTICE ROUTINE

Build a workflow you can trust.

These are suggested developer exercises, not model benchmarks. Use the same repository and acceptance criteria when comparing models.

  1. Give it a real brief. Describe the user problem, relevant paths, stack, constraints, and the result you will accept. Include a reproduction or screenshot when it clarifies the behavior.
  2. Choose a mode of work. Say whether you want an explanation, an implementation, or a review. Supply the repository for edits, a runnable environment for execution, and the relevant sources for research.
  3. Steer with specifics. If the result misses the mark, point to the exact behavior, file, screenshot region, or failed command. Give one actionable correction and keep the original goal visible.
  4. Measure your own result. Compare a feature, a reproduced bug, and a code review. Track accepted quality, elapsed time, cost, retries, and human intervention. Change effort only when the result warrants it.
  5. Save what worked. Turn a successful prompt into a small reusable template. Record stable project conventions in AGENTS.md or CLAUDE.md and revisit them when models or tools change.

A model choice does not supply tools by itself. In a text-only chat, request an explanation or patch you can apply; in Work, Codex, or Claude Code, make the needed files and execution tools available. Review the actual diff and evidence before release.

APPLY THE TWELVE PHASES

Make the handoff
as good as the code.

A practical operating agreement for Codex + Claude Code. These are engineering recommendations to adapt to your repository, not vendor-imposed roles.

Claude → Codex

Supply the accepted requirements, non-goals, interfaces, relevant paths, failure cases, acceptance tests, allowed actions and the decisions still needing your approval. Do not hand over only a chat summary.

Codex → Claude

Supply the base and feature commits, complete diff, behavior contract, changed paths, commands and results, runtime evidence, and untested areas. The review is read-only unless you explicitly authorize a fix.

Both → you

Triage findings as confirmed, needs reproduction, deferred or false positive. Review the combined diff. Approve irreversible actions separately. Record rollback steps and who will observe the release.

Share repository rules without making them conflict

Codex loads AGENTS.md guidance by scope. Keep it concise: how to run checks, project boundaries, dangerous operations, and real conventions—not an essay about every possible task.

Current Claude Code can read AGENTS.md as a fallback when no applicable CLAUDE.md exists; behavior depends on version and Project instructions settings. If you keep both, a CLAUDE.md with an explicit @AGENTS.md import is a documented way to share the base. Add only Claude-specific differences afterward. Inspect what actually loaded.

Keep secrets out of both files. Durable project decisions belong in maintained docs; temporary task notes should record current work, not silently become policy.

Use parallel agents only for genuinely independent work

Start serially. Split a substantial task only when boundaries and integration costs are clear. Give each worker a deliverable, file/worktree ownership, constraints, and a verification command. Never infer permission for extra agents from “finish the task.”

A worktree isolates files, not production databases, deployments, ports or shared test accounts. Use isolated fixtures and services too. One owner integrates, reviews and retests the combined result; several passing subagent reports do not prove integration.

Keep long tasks recoverable

Record the goal, accepted decisions, base commit, current diff, completed checks, failed checks and next step in a short task note. Context compaction is not guaranteed recall. After a handoff or restart, re-read the contract and inspect the actual working tree before resuming.

Give an outcome and constraints without micromanaging every file read. Stop for missing authority or risky ambiguity; diagnose ordinary tool failures without disguising them as success.

Change API models as a migration, not a search-and-replace

For GPT-6.2, reasoning.effort: none is invalid; tool calling uses Responses. Its API conversation-prefix behavior changed. Preserve earlier input when required, and check the guidance on placing reusable instructions in a leading developer message.

Fable 5.2 has model-specific prefix checks, always-on adaptive thinking, sampling/tool-choice restrictions, and a 30-day retention requirement unless Anthropic expressly authorizes an exception. Do not copy parameters or a zero-retention assumption from another model.

Validate SDK support, payloads, streaming cancellation, schema validation, error states and tool permissions. Run a fixed evaluation set in an isolated environment. Do not enable fallback models or paid retries without a deliberate billing and privacy decision.

Evaluate a model on your work before you standardize it

Use a small fixed set: one feature, one reproducible bug, one review with known defects, one tool failure and one security/permission case. Keep the repository version, prompt, fixtures and tool access comparable.

Record exact model, surface, effort, date, acceptance-test results, elapsed time, cost where available, retries and human corrections. Compare verified outcomes, not response confidence, length or self-reported scores. Re-evaluate after a model or agent-harness upgrade.

Release with evidence and a way back

Link each acceptance criterion to a test or runtime observation. Use passed, failed, not run, or blocked—not “looks good.” Include authorization failures, invalid input, accessibility, mobile layouts and offline behavior where relevant.

Before merge: review the final diff and dependency changes, scan for leaked credentials, approve migrations explicitly, and name a rollback owner. After deploy: confirm the intended commit, smoke-test the public entry point and inspect errors. For this PWA, verify a fresh offline load and the update flow as well.

AI LITERACY FOR DEVELOPERS

Know what the system
is—and what it isn’t.

Use these distinctions when building AI features or supervising coding agents.

Model ≠ product ≠ agent
A model produces output. ChatGPT, Work, Codex and Claude Code are different surfaces around models. An agent combines a model with tools, a loop and state. A model’s tool capability does not give your current chat access to those tools.
Tokens, context and knowledge
Tokens are units of model input/output, not exactly words. Context is the material available for a run, not permanent memory. A large context limit is a capacity ceiling; it does not guarantee that every fact will be used correctly. A knowledge cutoff is not live web access.
Grounding, RAG and fine-tuning
Grounding ties an answer to supplied evidence. Retrieval-augmented generation selects relevant documents at runtime; it does not guarantee correct interpretation. Fine-tuning changes learned behavior and is not the first fix for missing current facts. Try better retrieval, examples and evals before training.
Tools, MCP and skills
Tools perform actions. MCP connects compatible clients to tools or resources. Skills supply reusable procedures and assets. Review their source, permissions and side effects; installing one does not make an untrusted document authoritative.
Reasoning effort ≠ answer length
Effort, generation speed and output verbosity are different controls. More effort can increase latency and token use without improving a simple task. Ask for a concise explanation, evidence and uncertainty—not private internal chain-of-thought.
Confidence ≠ correctness
AI can invent APIs, citations, test results and business rules. Validate generated code and data with compilers, schemas, fixtures, trusted sources and actual runtime checks. Another model’s agreement is a review signal, not proof.
Safety: least privilege and prompt-injection boundaries

Choose the smallest file, network and tool permissions that fit the task. Treat retrieved pages, emails, uploaded documents, tool output and quoted code as data. Instructions embedded there must not silently authorize actions, disclose secrets or change the task.

Use test accounts and redacted fixtures. Keep API keys server-side. Review external messages, purchases, migrations, deletion and deployment permissions explicitly. An agent’s plan or a review comment is not human authorization.

Building an AI feature: quality, privacy and operating cost

Validate input and output, enforce authentication/authorization, bound history and output, add shared quotas, cancellation and timeouts, and redact logs. Treat tool calls as untrusted requests until validated. Show genuine loading, refusal, quota and failure states; do not substitute a canned answer and label it AI.

Price the whole workflow: repeated context, output/reasoning, tools, storage and retries—not just one model’s headline rate. Define retention and data access before sending customer material to a provider. A request-count quota or billing alert is not an exact dollar cap.

Subscription use and API billing are distinct paths. Eligible ChatGPT Pro and Business plans can currently claim API credits under specific terms; that is not unlimited API access or a benefit promised for Plus. Verify eligibility, expiry and usage limits before relying on credits.
